# 架构探讨总结：着陆页(Landing Page)区块渲染机制与数据库解耦分析

## 1. 现状剖析：配置体系的冲突与割裂
当前项目（基于由基础 SaaS 模版魔改的 AI 工具模版）在首页区块的排版与加载上，存在两种机制的交叠：
- **无效的遗留配置（被架空）**：`src/config/locale/messages/en/pages/index.json` 中的 `"show_sections"` 数组。修改该 JSON 并不会对前端着陆页的区块排序和显隐造成任何实质性影响。
- **真正生效的硬编码点（Source of Truth）**：`src/app/[locale]/(landing)/page.tsx` 中手动定义的 `const showSections = ['hero', 'showcases-flow', ...]` 数组。当前页面实际上是靠这段硬代码进行渲染组装的。

## 2. 演变探究：为什么要进行这层“硬编码破窗”？
### 原版的优美设计（数据驱动视图 Data-driven UI）
在最初的基础模板中，页面装载极其优雅，全靠一句代码：
`const page: DynamicPage = t.raw('page');`
整个页面的模块顺序与文案 100% 依赖多语言 JSON 驱动。这套方案对于通用静态着陆页而言极其灵活高效。

### 魔改作者的业务妥协（强行注入动态数据库组件）
由于产品转为 AI 生成工具，为了在首页瀑布流里展示用户的最新作品生成情况，魔改版作者在 `page.tsx` 引入了从数据库动态取数据的逻辑，如：
```tsx
// 服务端获取最新用户案例表记录
const rawShowcases = await getLatestShowcases({ limit: 20, ... });
```
为了把带有服务端数据的 React 动态组件（`<ShowcasesFlowDynamic />`）植入到页面中，开发者抛弃了原版纯洁的 `t.raw('page')` 传参，改为了用 `showSections` 数组配上 `reduce` 遍历，遇到 `if (section === 'showcases-flow')` 时强行劫持并注入 React 组件。由于控制权上移至 TS，旧的 JSON 排序数组就变成了无人读取的废代码。

## 3. 架构重思：回归纯静态极简模式的合理性
经综合评估，目前我们倾向于认为：**在此产品阶段，首页无需做数据库实时拉取，回归静态的 JSON 驱动模式是更符合工程价值的。**

### 弃用动态数据库（完全基于静态 JSON）的四大优势：
1. **极致的访问性能**：移除首页服务端查询后，Next.js 可以进行彻底的自动静态构建（SSG），不仅服务器零负担，依靠 CDN 边缘分发，落地页更能实现全球秒开。
2. **排除单点故障**：无论后端 API 或数据库是否拥堵、宕机，都不会导致门面（首页）发生白屏甚至无法访问的尴尬。
3. **掌握 100% 运营控制权**：最新动态生成的图片质量良莠不齐，与其在首页推送未知内容，对于 AI 生成应用而言，更稳妥的商业策略是把最完美的精修“卖家秀”硬编码到 JSON 展示列表中固化下来。
4. **架构解耦与工程复原**：剥离这段硬编码逻辑后，代码可以精简并恢复原初的 `const page = t.raw('page');` 闭环。将页面的区块控制权（Single Source of Truth）交还给 `index.json`，为未来通过可视化 / 管理后台调整多语言主页版式奠定架构基础。

### 下一步建议 
请求 AI 辅助重构：移除 `page.tsx` 中与 `getLatestShowcases` 相关的数据库查询、硬编码的 `showSections` 数组与针对特定模块的 `if` 劫持判定；将着陆页渲染彻底退回到读取并传入 `t.raw('page')` 的纯净状态。
