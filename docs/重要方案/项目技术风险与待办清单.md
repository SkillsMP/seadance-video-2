## 二、具体边界与最低验收

### R06｜游客上传（Cloudflare 已配置，先观察）

- **涉及**：`src/app/api/upload/route.ts`、`src/app/api/storage/upload-image/route.ts`，及 Cloudflare 限流、费用预警。
- **决定**：游客上传是正常产品功能，**不强制登录、不禁止匿名上传**。用户反馈已设置 Cloudflare，尚未独立核验规则是否生效及具体阈值。
- **剩余风险**：CF 限制的是请求频率，不限制单次文件大小。`/api/upload` 仍缺服务端文件大小/类型限制；`/api/storage/upload-image` 有单文件限制，但未限制整批数量/总大小。不能把 CF 视作所有问题已经解决。
- **现阶段只做**：用未登录浏览器一次选中 **30 张图片上传**；确认不被误拦，查看 CF Security Events 和存储费用。若正常批量上传被误拦，调整或暂停过严规则。
- **何时修代码**：发现真实滥用、超大文件、费用异常或上传故障时，再针对有问题的接口增加最小服务端限制，并兼顾批量上传体验。
- **不要做**：不强制身份验证、不新增账号配额系统、不重构上传链路。

### R04｜积分扣减（代码已修，待验证）

- **涉及**：`src/shared/models/credit.ts` 的 `consumeCredits()`。
- **当前代码**：`main` 已将 `batchNo` 改为按批递增、移除错误 `offset`，并检查是否扣足积分。
- **剩余工作**：在实际数据库验证零散积分、跨批次、余额不足和事务回滚；上线验证未确认。
- **不要做**：不改套餐、积分政策、历史账本和支付系统。

### R01｜Standard 时长（代码已修，待验证）

- **涉及**：`src/extensions/ai/kie.ts`。
- **当前代码**：`main` 已增加 `'bytedance/seedance-2': 'duration'`。
- **剩余工作**：模拟 Standard 10 秒生成，确认请求使用 `duration: 10` 而非 `n_frames`；确保其他模型不变。
- **不要做**：不重构整个 KIE Provider。

### R02｜参考视频成本（暂缓）

- **涉及**：Seedance Fast/Standard 的 `video-to-video` 定价。
- **风险**：本站按输出时长扣积分，参考视频输入可能有额外供应商成本，尚未确认发生实际亏损。
- **决定**：现在不改代码、不关闭功能、不改价格；实际调用增加或账单异常时，再核查 KIE 实际费用和本站积分收入。
- **不要做**：不提前建设动态计费引擎。

### R05｜失败退款并发（暂缓）

- **涉及**：`src/shared/models/ai_task.ts`。
- **风险**：旧逻辑先检查 ACTIVE，再退回积分并标记 DELETED；极端并发可能重复退款，尚未确认发生事故。
- **决定**：保留 ShipAny 原有实现；之前的原子退款补丁**暂不应用**。出现真实异常或明确的并发需求时，再按生产数据库类型定向修复和测试。
- **不要做**：不重构退款、支付或积分账本。

## 三、暂时不做（6 项）

| ID | 事项 | 什么时候才处理 |
|---|---|---|
| R03 | 无效 AI Callback 地址 | 确认供应商要求回调、现有无效 URL 影响创建，或未来修改共享 adapter 时；若可选，优先不发送无效地址，不为此新建 Webhook 平台 |
| R07 | 用户关页后任务缺少自动推进 | 出现无法找回/长期不结算的真实任务，或新模型必须依赖后台完成时；再考虑轻量定时补偿，不默认上队列 |
| R08 | 两处任务刷新逻辑重复 | 下一次确实修改任务查询/审核/结算时，抽一个共享函数；现在不单独重构 |
| R09 | 历史报价与旧方案混乱 | 使用到相关历史报价时清理冲突标记并更新日期，不为整理文档影响业务发布 |
| R10 | 模型配置与测试耦合 | 修改对应模型 factory 或测试时顺手减少重复字段、取消对生产 `enabled=true` 的硬编码断言 |
| R11 | 多数据库兼容层复杂 | 确认生产数据库和长期部署策略后再评估；**现在不动** Proxy 兼容层和数据库结构 |

> **暂缓不等于忽视**：R03/R07 如已造成真实任务无法完成或退款无法结算，应按实际故障提级，而不是机械等待“下次重构”。

## 四、Codex 执行边界

1. **一次只领取一个 ID**。先检查实际部署代码是否仍有问题，报告最小改动文件和影响范围，再修复。
2. 不修改无关模型、套餐、支付、数据库兼容层、Callback/队列；除非该 ID 的验收确实必须涉及。
3. 优先复用既有函数，**先补针对性回归测试，再做最小差异修复**；风险修复不能靠删除校验或关闭错误日志实现。
4. **提交前**记录：修改文件、原因、通过/未通过的测试、未核实风险、回滚办法；不能把“代码已改”写成“生产已修复”。
5. 不要求普通新模型接入顺带修完本清单；但本次模型直接涉及的阻断性计费/安全/协议问题必须处理或缩小开放范围。
