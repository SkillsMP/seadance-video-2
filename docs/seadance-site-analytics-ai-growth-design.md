# 网站埋点、业务分析与 AI 增长闭环实施设计

> 项目：seadance.video（ShipAny Two）
> 版本：V1 精简实施稿，2026-09-17
> 依据：四人方法精华整合，以及用户提供的哥飞关于事件表和后台 MCP 的两段分享。
> 状态：V1 代码已实现；迁移文件已生成，线上数据库迁移与真实流量验收待执行。

## 0. V1 范围与完成标准

目标：补齐“访客 → 注册 → 使用 → 付费”的行为过程，关联现有业务表，让 AI 能根据真实数据与代码找到转化卡点。

**V1 只做：**

- 一张 events 表、一份事件字典、客户端 track() 与服务端 recordEvent() 双入口。
- 接入访客、认证、生成、结果查看和购买主链路，复用现有用户、任务、订单及积分记录。
- 三类受控查询：获客与商业转化、产品使用、失败与成本；输出简单 JSON/报告供 AI 分析。
- 复用已有 GSC/Bing 脚本和 GA 基础能力；events 预留可空 build_id，有现成构建标识就记录。

**V1 明确不做：**

- 版本人群归因、版本选择器、跨版本对比及长期聚合报告系统。
- GA4 业务事件同步、Measurement Protocol、GA4 漏斗 API、新 BI 后台。
- MCP 接入、任务发布工作流、自动改版或自动切换模型。
- 通用事件总线、消息队列、身份图谱、多数据库重构。

与精华文档的差异：本仓库采用“自建优先、GA4 按需接入”，共享事件定义而非一律浏览器双写。purchase 和任务终态由服务端确认，避免浏览器漏报、重复上报污染业务事实。

V1 完成标准：主链路可关联，失败原因可解释，事件与业务表能抽样对账，统计故障不改变已有业务结果。具体边界集中在第 2 节，后续能力见附录。

## 1. 设计依据与当前基础

### 1.1 四人思路的分工

| 来源 | 本方案吸收的原则 |
| --- | --- |
| 虾哥 | 搜索、行为、收入分层诊断；先确认数据可信，再按周期复盘 |
| Niko | 围绕实际问题找异常，结合用户反馈，不因小样本搭建复杂分析平台 |
| 王焱 | 统一事件字典、参数白名单、失败分类、验收与报表口径 |
| 哥飞 | 自建事件表关联具体业务，让 AI 对照代码分析；通过后台 MCP 读取任务、写回内容并发布 |

哥飞的两段分享对应两种能力：

1. **分析能力**：自建行为日志关联用户、订单、生成记录，AI 基于真实漏斗提出改进。
2. **执行能力**：后台暴露 MCP，AI 读取已有任务，完成页面/文章内容，写回并发布。

两者可以独立落地。V1 先让数据能回答问题，已有查询服务以后再通过 MCP 暴露。第三方平台也可以实现部分身份关联；自建的优势在于能够直接复用本项目的数据关系和业务定义，不必宣称第三方完全做不到。

MCP 是能力接口，不提供模型额度。“不额外支付 API 费用”取决于所用客户端的订阅、额度和条款，不作为本项目的技术承诺。

## 2. 硬约束

1. user、ai_task、order 是注册、任务和支付真值，events 补充行为过程及业务关联。
2. purchase、generation_* 任务状态和 sign_up 由服务端确认；浏览器只采集交互及本地失败。
3. 统计写入在既有业务提交后执行，独立处理错误，保持扣费、退款和支付事务原样。
4. 服务端使用平台支持的生命周期机制或有界等待，测量额外开销；统计失败留下简短日志，业务结果保持原样。
5. 复用现有认证、db()、共同支付服务与错误分类，接入点使用直接函数调用。
6. 唯一 ID/幂等键防止重复计数；事件只参与分析，不参与授权、计费或任务状态判断。
7. 行为采集遵循显式拒绝状态，只保存必要字段；当前仓库没有统一 consent UI，V1 读取 `analytics_consent=denied` 关闭发送，后续接入授权 UI 时沿用该开关；接口校验身份、关联归属和输入大小。
8. 采集可关闭，schema 使用增量迁移；每次接入核对相关 diff 与业务回归。

允许少量行为事件丢失，以业务表检查覆盖率。V1 不增加自动补录或可靠消息基础设施。

## 3. 统一事件字典与触发语义

V1 保留 14 个事件，按主链路逐步接入。landing_view 用于记录到达但没有操作的访客，是获客漏斗的必要分母。

| 事件 | 唯一触发定义 | 权威来源 / 去重范围 |
| --- | --- | --- |
| landing_view | 同意采集后，当前分析会话首次呈现的落地页 | 浏览器；每分析会话一次 |
| tool_start | 用户首次实际操作生成器，如编辑输入、选择素材或模型 | 浏览器；每页面实例、每工具一次，挂载不算使用 |
| upload_completed | 素材上传接口确认成功 | 浏览器；每次上传操作一次，不传文件名或资源 URL |
| generation_submit_failed | 创建任务前提交被拒绝或请求失败 | V1 由浏览器记录前置校验与未收到明确结果的请求失败；任务是否创建、任务终态由服务端事件和业务表确认；完整 attempt_id 聚合后置 |
| generation_started | 本地任务记录及既有相关事务成功提交 | 服务端；每 ai_task.id 一次，按钮点击不算 |
| generation_succeeded | 本地任务首次被确认进入成功状态 | 服务端；每任务一次，轮询不重复计数 |
| generation_failed | 已创建任务首次被确认进入失败状态 | 服务端；每任务一次，客户端断网不等于任务失败 |
| result_view | 结果已呈现且进入可视区域 | 浏览器；每页面实例、每任务一次 |
| download_result | 用户发起结果下载 | 浏览器；每下载操作一次，仅代表意图，不承诺文件保存成功 |
| sign_up | 新用户记录创建成功 | 服务端；每 user.id 一次 |
| login_complete | 登录成功并确认取得有效会话 | 认证成功节点；每次成功登录一次，页面刷新不重复 |
| pricing_view | 价格页或付费面板实际可见 | 浏览器；每页面/面板展示实例一次，点击 Upgrade 不等于曝光 |
| checkout_started | 已创建订单且支付商返回有效 Checkout 会话 | 服务端；每订单、每 Checkout 会话一次 |
| purchase | 服务端验证支付结果且订单更新为已支付 | 共同支付服务；每实际收款对应的订单一次 |

V1 先按单次客户端事件记录提交失败，不据此计算提交失败率；后续需要把一次点击的多次校验/网络失败合并时，再引入 attempt_id。浏览器只补报未收到明确服务端拒绝响应的网络失败；即使稍后发现任务创建成功，也不能把该网络异常计入任务失败率。

身份类事件在实施前核对现有认证回调，选择一个成功入口。浏览器不能任意声明新用户注册成功。登录事件本身不代替 user.createdAt 的注册事实。

### 3.1 公共上下文

- tool：稳定功能枚举，例如 text_to_video、image_to_video；不以 URL 作为功能名。
- media_type、model、provider：任务事件使用服务端实际记录；请求模型与最终执行模型不一致时，按实际任务分析。
- locale、surface：复用当前语言和入口，surface 固定枚举，避免自由文本。
- plan：在有关事件中带入实际业务套餐；无需为所有事件强行查询套餐。
- task_id、order_id：指向本地 ai_task.id、order.id，不能与供应商 taskId 混用。
- page_path、referrer_host：保留规范化入口，移除敏感查询参数；UTM 有现成可信来源时按需记录，完整广告归因后置。
- 套餐与 billing_cycle：优先在查询中关联订单现有字段；事件仅保存确有需要的快照，兼容一次性积分包。

未适用的字段留空。缺失与 unknown 分开解释，不为了报表整齐伪造模型或渠道。

### 3.2 错误与耗时

复用生成接口已有错误分类，在分析边界映射为 validation_error、upload_error、quota_limit、moderation_blocked、provider_error、timeout、network_error、unknown。支付错误独立分析，不塞入 generation_failed。

任务耗时从服务端任务创建到本地首次确认终态计算，明确它可能包含排队和轮询确认延迟，不称为供应商精确推理时长。缺少终态时间时不使用任意 updatedAt 冒充完成时间。

视频生成初始分桶建议为 lt_30s、30_60s、60_120s、120_300s、gte_300s，各区间左闭右开；负数或非有限值视为缺失。原始 duration_ms 留在内部用于分位数计算，分桶边界以后按真实分布调整并记录字典版本。

## 4. Events 表：只新增必要数据

### 4.1 字段方案

在 src/config/db/schema.postgres.ts 中沿用 table 包装和现有文本主键习惯。当前启用 PostgreSQL，先完成这一方言；SQLite/MySQL 在实际需要支持时按相同契约补齐，不同时重构数据库层。

| 字段 | 用途 |
| --- | --- |
| id | 事件唯一 ID；客户端为同一次操作生成一次并在有限重试中复用 |
| dedupe_key | 可空唯一键；服务端业务节点使用 event_name + 实体 ID 等稳定组合 |
| event_name、schema_version | 白名单事件；schema_version 初始固定为 1，口径确有变化时再升级 |
| build_id | 可空预留字段；有现成标识时记录事件产生端版本，缺失留空；V1 不要求改造构建或登记版本 |
| occurred_at、received_at | 事件发生时间与服务端接收时间；客户端时间需校验合理范围 |
| source | client / server，由接收入口赋值 |
| anonymous_id、user_id、session_id | 可空分析身份；user_id 从服务端认证读取，session_id 不使用认证 token |
| page_path、referrer_host | 可空页面上下文；Webhook 不强制要求页面路径 |
| task_id、order_id | 可空业务关联，使用本地 ID |
| tool、model、locale、surface | 常用筛选维度 |
| properties | 有白名单和大小上限的 JSON，保存耗时、错误枚举、UTM、套餐等扩展值 |

初始只建立 dedupe_key 唯一约束，以及 event_name + occurred_at、user_id + occurred_at、anonymous_id + occurred_at 索引。任务/订单索引根据实际查询再补，避免给每个字段建立索引。

扩展 JSON 不复制 Prompt、结果内容、资源地址、原始异常栈或支付响应。需要诊断时通过 task_id/order_id 关联受控业务查询，报告默认输出摘要。实体删除后事件关联如何清理或置空，须与项目现有删除流程保持一致，不能新增阻止用户删除的外键约束。

### 4.2 身份关联与最小采集约束

同意分析采集后生成匿名 ID 和分析 session_id；session_id 可采用 30 分钟无活动重新生成的简单规则。登录成功时服务端用已验证用户与当前匿名上下文建立关联，记录在登录事件中，V1 无需额外身份图谱表。

查询只关联该登录前相应匿名会话内的事件；不把同一设备所有历史都归给最后登录的人。退出登录或切换账号后轮换匿名上下文。拒绝/撤回采集时停止行为保存与发送，清除待发数据；不补发拒绝期间的活动。未同意期间也不缓存行为历史，降低实现复杂度。

注册、任务、订单等必要业务记录继续按既有流程保存。分析数据用途和明细保留期在上线前按附录 D 确认，沿用现有业务数据保留规则。

客户端事件接口只允许客户端事件、限定体积与批量大小，复用已有请求限制能力。关联任务/订单时校验归属，user_id、业务状态和收款金额不能由客户端自行指定。客户端数据是行为信号，不用于财务结算。

## 5. 双入口写入与模块接入

```text
浏览器交互 → track() → 事件接收 API → events
业务提交完成 → recordEvent() → events
events + user / ai_task / order / credit → 聚合查询 → AI 分析
```

| 建议模块 | 单一职责 |
| --- | --- |
| src/shared/lib/analytics/events.ts | 事件类型、参数白名单和枚举，无 React/数据库依赖 |
| src/shared/lib/analytics/track.ts | 浏览器上下文、同意状态与行为发送 |
| src/shared/services/analytics-events.ts | 服务端可信上下文、幂等记录、业务事件与三类分析查询 |
| src/shared/models/event.ts | 复用 db() 读写 events |
| src/app/api/analytics/events/route.ts | 仅接收允许由客户端上报的事件，调用服务层 |
| src/app/api/analytics/funnel/route.ts | 管理员权限保护的聚合报告入口，不返回原始事件 |

业务接入只调用采集函数；数据库访问集中在 model，统计口径集中在 service。自建事件服务与原有第三方 analytics service 分开，支付在共同业务层接入，避免为不同支付商复制采集逻辑。

## 6. 三类查询与使用节奏

### 6.1 三类核心报告

| 报告 | 口径 | 解决的问题 |
| --- | --- | --- |
| 获客与商业转化 | landing_view → sign_up → checkout_started → purchase；同时查看登录老用户和直接购买分支 | 哪些入口带来真实注册和付费 |
| 产品使用 | tool_start → generation_started → generation_succeeded → result_view → download_result；图生视频另看上传步骤 | 用户在哪个阶段停止 |
| 失败与成本 | 提交拒绝、任务失败分别统计；关联模型、耗时、积分消耗和退回 | 输入约束、请求问题、Provider 问题各占多少 |

实施时先依据真实登录要求画路径，不能预设“生成完成后才登录”。已登录用户、先看价格后购买的用户不强行经过所有步骤。

必须分别定义：

- 用户漏斗：按已验证用户或可关联的匿名会话去重，检查步骤顺序，并明确时间窗口；默认先报告同会话转化，跨会话付费另用已验证用户的 7 天窗口。
- 任务成功率：按任务创建日期取 cohort，成功任务 / 已终态任务，同时列出处理中数量及观察截止时间。
- 提交失败：按 attempt_id 去重统计创建前失败次数和原因，单独展示。V1 没有完整提交尝试记录时不输出失败率，不能拿已创建任务数作分母。
- 收入：按 order 的已支付状态、paidAt 与实际支付金额统计；退款、续费和首购分别标注，币种不直接相加。

各事件总次数相除不等于有序用户漏斗。每份报告输出分子、分母、时间范围、覆盖率及口径版本；新埋点上线前的数据不与完整链路混算。小样本先看个案和数据质量，30 个会话、10 个业务事件等只能作为初始观察提示，不是统计显著性保证。

### 6.2 样本、覆盖率与复盘

各事件总次数相除不等于有序漏斗。报告优先显示人数、次数、分子/分母和观察区间，再显示百分比。

| 观察条件 | 使用方式 |
| --- | --- |
| GSC 曝光 < 100 或点击 < 10 | 仅记录趋势，不据此判断 SEO 改版成败 |
| 会话 < 30 | 互动与转化变化只作为排查线索 |
| 业务事件 < 10 | 先核对事件到达、参数和关联，暂不评价漏斗 |
| 连续收入观察 < 7 天 | 暂不作稳定收入归因 |

以上为实务提醒，不是显著性标准。参数缺失或 GA4 的 (not set) 占比持续偏高，应检查事件是否需要该参数、接入是否遗漏及是否混入旧数据；不必新增覆盖率平台。

| 时间 | 复盘重点 |
| --- | --- |
| 上线当次 | 跑通成功和失败路径，检查数据库关联和重复计数 |
| 24–48 小时 | 数据是否持续到达、参数是否完整、业务表抽样对账 |
| 7 天 | 排查持续缺失与明显异常，记录用户反馈 |
| 14 天 | 在同一口径和合理样本下观察漏斗 |
| 28 天 | 结合已有 GSC/Bing 报告看搜索表现；不足则延长观察 |

AI 读取报告和相关代码，输出“证据 → 假设 → 建议修改点 → 验证方式”。用简单改动日志记录日期、页面、预期指标，沿用既有开发发布流程；V1 无需版本归因系统即可开始复盘。

GA4 业务同步按附录 A 后续接入；MCP 按附录 B 复用已完成的查询。二者均不阻塞 V1。

## 7. 实施顺序、验收与回退

| 阶段 | 交付 | 验收重点 | 状态 |
| --- | --- | --- | --- |
| 基础核对 | 现有实体、登录顺序、支付入口、搜索脚本清单 | 实际路径与文档一致 | 已完成局部静态核对，线上待验 |
| V1-A 采集基础 | 事件字典、events 增量迁移、track、接收 API、recordEvent、可空 build_id 预留 | 代码已实现；迁移已生成，待执行数据库迁移与采集开关验收 | 已实现，线上待验 |
| V1-B 主链路 | 按真实入口接入注册、生成、结果、Checkout、收款 | 原业务返回值、状态、扣费与退款不变 | 已实现，线上待验 |
| V1-C 读取与分析 | 三类受控查询、缺失检查、首份 AI 诊断 | 代码与聚合测试已完成，待有真实事件后抽样对账 | 已实现，数据待积累 |
| V2 版本分析 | 版本登记、人群归属、对比及历史报告留存（附录 C） | 单独实施与验收，不阻塞 V1 | 后续 |
| 可选 GA4 | 适配与分析脚本、报表配置 | 标准参数、归因和覆盖差异可解释 | 按需要实施 |
| 后续 MCP | 先只读查询，再任务/内容写回发布 | 复用服务、权限和实际发布流程 | 规划 |

验收至少覆盖：

1. 新访客 → 注册 → 生成 → 看结果 → Checkout → 支付，以及老用户直接生成/购买。
2. 图生视频上传、前端校验失败、服务端提交拒绝、真实任务失败、页面关闭后完成。
3. 刷新、重复轮询、支付回调与通知重复到达，不增加重复业务事件，也不重复扣积分或发权益。
4. 统计接口超时/异常、数据库事件写入失败、关闭采集开关，原有生成、登录、支付与退款仍按原逻辑完成；记录延迟开销。
5. 拒绝/撤回分析、退出登录、切换账号，不补发历史、不串联不同用户。
6. 业务记录与事件抽样校核，SQL 分母/去重/顺序验证。
7. 检查 diff 仅包含必要接入点，运行相关类型检查与已有回归测试，不为本方案进行无关重构。
8. build_id 为空仍能完成采集和三类查询；有值时保留事件产生端标识。版本对比、GA4、MCP 不属于 V1 验收。

关闭分析开关即可停止新增采集，保留已有业务路径。迁移回退不删除业务表；是否保留 events 按数据保留规则处理。MCP、GA4 和自动报告均不得成为网站正常运行的前置依赖。

## 附录 A：可选 GA4，V1 完成后按需接入

### A.1 接入契约

自建报告独立可用后，再决定哪些事件需要同步到 GA4。保留现有 GA 基础能力，GA4 配置与事件可用性单独验收；不因新增自建采集而顺手调整现有页面统计。

共享事件字典不等于所有事件都从浏览器双写：

- 客户端行为可以由 track 分发给可选 GA4 适配器。
- 服务端业务事件如果要进入 GA4，由服务端适配器负责；浏览器不再次上报同一 purchase 或任务终态。
- Measurement Protocol 需单独配置服务端凭据，并在用户允许采集时保存所需 client_id/session_id 关联。内部分析 session_id 不冒充 GA4 session_id，不能为缺失归因伪造标识。
- GA4 发送失败不影响业务或内部报告；V1 不新增补偿队列，报告注明覆盖差异。

低基数限制主要针对自定义分析维度。purchase 的 value、currency、transaction_id、items 按标准电商语义发送，不因“禁止原始金额/ID”全部剔除；transaction_id 使用稳定且不含个人信息的交易标识，不注册为高基数自定义维度。金额按币种和项目存储单位正确转换，不能对所有币种机械除以 100。

上线前核对实际媒体资源的自定义维度、数据保留设置、生产环境采集控制和支付商引荐排除。生产 Host 的采集限制与报告筛选分别处理，不能靠传一个自定义 hostName 参数自动过滤预览数据。

### A.2 数据读取

复用 V1 的内部查询。只有需要 GA4 报告时才增加下述脚本。

可选 ga4_analytics.py 使用 GA4 Property ID 和具备该资源读取权限的凭据，不能把 GSC 权限等同于 GA4 权限。普通聚合使用 Data API；有序漏斗需使用专门的 runFunnelReport（当前 v1alpha）或内部事件查询，不以普通 eventCount 报表冒充。

GSC/Bing 与站内报告按规范化页面和日期聚合关联。GA4 会话数与 GSC 点击数本就不是同一口径；异常只能产生待验证假设，不能凭低互动率直接判定文案或 Provider 是根因。

## 附录 B：后续 MCP，复用查询与内容服务

### B.1 第一阶段：复用读能力

当需要从支持 MCP 的客户端访问后台时，再暴露：

- get_funnel：有序转化、人数、时间窗和覆盖率；版本筛选和历史报告读取仅在附录 C 实现后增加。
- get_generation_failures：任务失败与创建前拒绝的分类摘要。
- get_revenue_summary：订单确认的收入、付费用户、首购/续费。
- get_user_journey：经过权限校验的单用户事件及业务记录摘要。
- get_page_performance：页面行为与搜索聚合表现。

MCP 调用同一查询服务，不重新实现统计，也不开放任意 SQL 或整库原始读取。按已有管理员权限控制，默认聚合返回，单用户诊断按需使用。

### B.2 第二阶段：哥飞的任务与内容写回流程

```text
读取后台任务 → 获取页面/文章上下文 → AI 生成内容
    → 保存草稿与修改摘要 → 校验/预览 → 发布 → 写回任务结果 → 观察数据
```

按实际需求提供 list_tasks、get_task、save_content_draft、publish_content、complete_task。复用已有文章服务、权限校验与发布能力；没有后台任务系统时先用现有任务载体，不为了 MCP 新建完整工作流平台。

文章和代码驱动的页面区别处理：可由现有后台保存的文章走内容服务；依赖仓库 JSON/组件的页面走代码变更与部署流程，不能假设写一条数据库记录就能发布动态页面。

写入返回实体 ID/版本和结果；发布复用已有状态检查，避免重复调用重复发布。修改和发布遵循用户授权范围。自动切换模型、改价、退款不属于内容发布能力，不纳入 V1。

## 附录 C：V2 版本归因与改版对比

启动条件：V1 主链路与三类查询稳定，并已有需要比较的多次改版。V1 仅预留可空 build_id，以下登记、归属和报告能力独立实施。

**版本身份与登记**

- 构建时生成统一的 build_id 并编入页面与服务端，使用完整 Git 提交号标识代码版本；短哈希仅用于展示。同一提交因配置变化需要重新比较时，附加部署/构建标识区分。
- 客户端到达及行为事件携带实际页面版本，不能在接收端用当前服务端版本覆盖。服务端业务事件记录服务端版本；旧标签页与新服务端同时存在时允许两者不同。
- schema_version 表示事件口径，build_id 表示应用版本，两者独立。无需每次提交都改变事件字典版本。
- 复用现有 config 表保存版本元信息，建议每个 build_id 一个独立键（如 funnel_build:<build_id>），包含提交说明、短哈希、构建时间和首次生产部署时间。避免反复覆盖一个不断增长的 funnel_builds JSON 列表，也不新增版本管理服务。
- 登记由部署后的受控步骤幂等执行；缺少部署接入时，可由已认证的后台首次访问作为补充登记入口。登记失败只影响显示名称，以短哈希兜底，不影响采集。历史版本记录持续保留。
- 默认显示“提交说明 + 短哈希 + 部署日期”，不要使用事件最近出现时间判断“线上”。线上标记由当前生产部署信息提供，回滚时同步更新；灰度多版本并存则如实列出，未核实时不显示该标记。

**事件版本与归属版本分开统计**

事件版本回答“这一步实际在哪个版本发生”；归属版本回答“首次接触该版本的这批人，后来转化得怎样”。归属版本由查询选取首次 landing_view 计算，避免在每条事件冗余维护，也不改写用户表。

1. 报告固定获客区间 [开始, 结束)、观察截止时间、身份规则和转化窗口。访客归属于该获客区间内首次可识别 landing_view 的 build_id；已验证身份按第 4.2 节规则关联，无法关联的设备不强行合并。
2. 示例：访客在 A 版本首次到达，次日在 B 版本返回并付款。在同一固定 cohort 的 7 天观察窗中，仍计入 A 的获客转化；付款事件实际版本仍记录为 B。不能把该付款解释为只由 A 的界面促成。
3. 查询先选定归属人群，再查询其窗口内后续行为与业务事实，不能把所有步骤简单加上 build_id = A 的过滤，否则跨版本转化会被错误丢弃。产品同会话漏斗仍使用原同会话窗口。
4. 改变获客区间会改变“区间首次到达”的定义，生成新的报告 cohort；若需要终身首次版本，则是另一种明确命名的口径。已保存报告不随日期选择器变化重算覆盖。
5. 没有版本字段的老数据单列 unknown/版本记录前。无可用 landing_view 的用户单列未归属，不根据订单发生时的版本倒推首次接触版本。

**对比报告与长期留存**

按版本输出到达、开始使用、注册、创建任务、生成成功、看到结果、Checkout、付费的人数及阶段转化率，并保留样本量、观察窗是否成熟、事件覆盖率和跨版本回访人数。不同路径沿用第 6.1 节分支定义，不照搬参考案例的引导/对话阶段。

需要后台展示时，版本选择器按部署日期排序；阶段表、渠道/广告、落地页等子报告使用同一归属人群和筛选条件。广告维度仅在实际记录相应 UTM/广告标识时显示，不假设已有投放数据。

为避免 90 天明细到期后失去改版记录，每次复盘保存一份不含个人标识的聚合报告，含版本元信息、变更说明、获客区间、观察截止、口径版本、分子/分母及生成时间。复用报告导出能力和现有持久存储，以独立报告 ID 留存；不只保存“最新结果”。观察窗未结束的报告标为暂定，成熟后另存最终报告。明细到期后的历史报告仅支持已保存维度，不承诺任意重新下钻。

AI 对比时检查渠道、设备、新老用户组成和观察时长。版本前后转化差异属于改进效果的证据，不能仅凭版本号证明因果；跨版本暴露、小样本或口径变化须在结论中说明。先依靠固定窗口与变更记录提高可比性，不为此引入 A/B 平台。

V2 单独验收：A 到达、B 回访/付款仍按固定 cohort 归 A，实际事件版本为 B；旧标签页、回滚、缺失版本、未归属数据分别验证。各子报告筛选一致，历史聚合报告在明细过期后仍可读取。

## 附录 D：上线前的数据用途与保留期确认

V1 需确认采集同意界面的衔接、行为数据用途、删除方式和保留期限。90 天可作为明细保留候选值，结合实际隐私说明确定；必要的订单等业务记录沿用原规则。此项是上线配置决策，不要求构建隐私管理平台或长期聚合存储系统。
