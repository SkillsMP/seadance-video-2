# 前台定价与积分扣费 AI 配置文档

本文件是 AI 修改前台 pricing 和生成扣费配置的执行规范。

业务定价来源：

- `docs/定价/3.本项目定价方案.md`

主从关系：

- `3.本项目定价方案.md` 是唯一业务定价源，负责维护前台套餐表、模型积分消耗表、积分锚点和执行边界。
- 本文件只维护改代码时的文件范围、字段规则、支付核验、落地步骤和验收清单。
- 本文件不要重复维护完整 SKU 表或完整模型积分消耗表；价格、积分、family、场景等具体数值以 `3.本项目定价方案.md` 为准。

---

## 1. 优先改动范围

常规改前台套餐时，优先只围绕这 2 个文件处理：

| 类型 | 文件 |
|---|---|
| Pricing 英文配置 | `src/config/locale/messages/en/pages/pricing.json` |
| Pricing 中文配置 | `src/config/locale/messages/zh/pages/pricing.json` |

图片 / 视频新增模型或调整模型积分时，默认只改两处：

1. `docs/定价/3.本项目定价方案.md` 第 3 节「模型积分消耗表」。
2. `src/config/ai/models.ts`。

`src/config/ai/credit-costs.ts` 从 `models.ts` 的 `pricing` 字段计算扣费，只在调整扣费查找策略、pricing 模式或新增媒体类型等计算规则时修改。图片 / 视频生成器的 `MODEL_OPTIONS` 也从 `models.ts` 派生，不再手工同步。

支付映射、前台展示、免费额度只作为注意事项核对，不作为默认改动范围。

不要在常规改价任务里顺手做：

- 新增 `plans.ts`。
- 新增 `credit-policy.ts`。
- 改支付 webhook / checkout。
- 改积分账本模型。
- 做年付按月发放计划任务。
- 做 provider / model 全量白名单系统。
- 做根据 fallback 成功结果动态二次计费。

## 2. Pricing SKU 配置规则

`pricing.json` 是前台套餐配置源。英文和中文 pricing JSON 的结构字段必须一致，只翻译文案。

SKU 的业务数值来源：

- 套餐数量、产品线、档位、售价、积分、有效期、发放方式，以 `docs/定价/3.本项目定价方案.md` 第 4 节「前台套餐表」为准。
- 不要在本文件维护第二份 SKU 表。

配置规则：

- `amount` 使用货币最小单位，例如 `$14.90` 写 `1490`。
- `product_id`、`interval`、`group`、`amount`、`currency`、`credits`、`valid_days` 在 en / zh 中必须完全一致。
- 只翻译 `title`、`description`、`features`、`tip`、`button.title`、FAQ。
- 不要翻译或改写 `product_id`。
- `payment_product_id` 不确定时不要填假值；要么填真实支付 Price ID，要么确认当前动态价格模式可用。

`group` 和 `interval` 的职责不要混用：

- `group` 控制前台 Pricing Tab 分组，当前组件按 `item.group === group.name` 过滤。
- `interval` 控制支付周期，当前可用值为 `one-time`、`month`、`year`。
- 当前映射关系是：一次性积分包 `group=one-time / interval=one-time`，月付订阅 `group=monthly / interval=month`，年付订阅 `group=yearly / interval=year`。

Pricing 组件已经按可见 item 数量使用静态 `md:grid-cols-*` class 做布局兜底。后续不要为了 SKU 数量再重构 pricing 组件。

## 3. 生成扣费配置规则

模型注册与扣费业务数据：

```text
src/config/ai/models.ts
```

扣费计算入口：

```text
src/config/ai/credit-costs.ts
```

模型扣费业务数值来源：

- 当前已落地项目中，模型注册和扣费执行口径以 `src/config/ai/models.ts` 为准。
- `docs/定价/3.本项目定价方案.md` 第 3 节「模型积分消耗表」是新增 / 调整图片和视频模型时的业务定价源。
- 新增模型或改价格时，先更新定价文档第 3 节，再由 AI 同步 `models.ts`，最后校验代码执行口径与业务定价一致。
- 不要在生成器里手写第二份模型列表，也不要在 `credit-costs.ts` 手写第二份模型积分消耗表。

当前图片 / 视频扣费不再使用 legacy scene fallback。

图片和视频统一通过 `src/config/ai/models.ts` 的 `pricing` 字段计算：

- image 使用 `fixed` pricing。
- video 使用 `perSecond` pricing。
- resolution 通过 `byImageResolution` / `byResolution` 控制。
- 不同输入口径通过 `scene + skuAttributes.inputBilling` 区分。
- 最终扣费由 `resolveGenerationPricingSnapshot()` 调用 `calculateModelCredits()` 得出。

legacy scene fallback 仅保留给非图片 / 非视频路径，例如：

- music / text-to-music: 10

如果 image / video 未命中明确 `pricing`，应直接报错，不应回落到固定 scene fallback。

实现要求：

- 以 `src/config/ai/models.ts` 里的真实 `family` 字符串为准，不要凭模型展示名猜 key，不要把分辨率拼进 family key。
- 如果 `3.本项目定价方案.md` 中的 family、分辨率 key 或扣费数值还没有在当前代码里出现，AI 必须按该业务定价源在 `models.ts` 新增或校正模型注册和 pricing，再运行校验。
- 当前图片 / 视频前端传的是 `family + candidates`，后端在 provider fallback 选出 `finalModel` 之前就要做余额校验，所以必须先按 `family + scene` 解析模型，再结合 `pricing`、分辨率、输入口径和时长定价。
- 只有在单独处理了 `candidates` 最高价预校验和 `finalModel` 实际扣费记录后，才考虑 `model override`。
- 文件必须保持纯 TypeScript。
- 不 import 数据库。
- 不 import env。
- 不 import `server-only`。
- 不从 `src/config/index.ts` 重新导出。
- 判断价格是否存在时用 `typeof cost !== 'number'`，不要用 `if (!cost)`。
- 前端余额不足只是体验提示，最终以后端校验为准。

`credit-costs.ts` 的扣费计算应从 `MODELS` 派生，legacy fallback 不得覆盖 image / video 的明确 pricing。固定积分结构等价于：

```ts
const FAMILY_CREDIT_COST_OVERRIDES = MODELS.reduce<
  Record<string, Partial<Record<string, number>>>
>((costs, model) => {
  // derive model.credits by family + scene
  return costs;
}, {});
```

示例只说明派生方向，具体 family、pricing 和 credits 必须先在 `3.本项目定价方案.md` 第 3 节确定业务口径，再由 AI 同步落地到 `src/config/ai/models.ts`。

### 3.1 新增模型 / 新增供应商维护规则

以后新增模型时，不需要修改前台套餐表。套餐表只决定用户怎么买 Credits；模型积分消耗表先确定业务扣费口径，`models.ts` 的模型注册和 pricing 负责执行每次生成扣多少 Credits。

#### 已有供应商新增模型

如果只是给当前已经接入的供应商新增一个图片 / 视频模型，默认只修改 2 个地方，并且先改业务定价文档，再由 AI 同步代码：

1. 在 `docs/定价/3.本项目定价方案.md` 的「模型积分消耗表」中新增或调整一行或多行，明确：
   - 媒体类型
   - 模型 / 能力名称
   - 代码 family key
   - 供应商 / route
   - 场景
   - 积分
   - 成本与毛利说明

2. 由 AI 按业务定价源同步 `src/config/ai/models.ts`，新增或调整一条或多条 `ModelEntry`，包括：
   - `mediaType`
   - `family`
   - `value`
   - `label`
   - `provider`
   - `scenes`
   - `enabled`
   - `credits`
   - `pricing`
   - 必要时填写 `skuAttributes`、`controls`、`defaults`、`enforced`

不要为图片 / 视频新增模型手工修改生成器 `MODEL_OPTIONS` 或 `src/config/ai/credit-costs.ts`。生成器选项和扣费都会从 `models.ts` 派生。

注意：`credits` 和 `pricing` 必须按 `scene` 配置，不要只按 family 写一个总价。

示例：

```ts
{
  mediaType: 'video',
  family: 'sora-2-pro',
  value: 'sora-2-pro-text-to-video',
  label: 'Sora 2 Pro',
  provider: 'kie',
  scenes: ['text-to-video'],
  enabled: true,
  credits: { 'text-to-video': 60 },
  pricing: {
    'text-to-video': {
      mode: 'perSecond',
      defaultDuration: 5,
      creditsPerSecond: 12,
    },
  },
}
```

#### 新增全新 API 供应商

如果是新增一个当前项目还没有接入过的 API 供应商，通常还需要额外处理：

1. 新增 provider 实现文件。
2. 注册到 AI 服务初始化逻辑。
3. 新增 API Key / custom storage 等配置项。
4. 更新 `.env.example` 或后台 settings 配置。
5. 更新 `/api/ai/providers` 的可用性判断。
6. 在 `docs/定价/3.本项目定价方案.md` 的模型积分消耗表中新增对应 route。
7. 在 `src/config/ai/models.ts` 中新增对应 `ModelEntry`。
8. 完成生成、查询、失败、扣费、余额不足等测试。

#### 高成本供应商限制

如果新供应商的同名模型成本明显高于当前低成本 route，不允许直接塞进已有低价 family 的 fallback 链路。

例如：

- KIE Veo Fast = 45 credits
- 某高成本供应商 Veo Fast = 应按 120 / 180 credits

这种情况不能让高成本供应商沿用 45 credits。

处理方式：

- 拆成独立 family；或
- 后续升级为 `family + scene + provider / route` 定价；或
- 不接入该高成本 route。

第一版优先保持简单：`family + scene -> credits`。

## 4. 注意事项

### 4.1 支付配置

`product_id` 是 checkout、订单、支付 provider 映射的核心字段。en / zh 必须完全一致。

`payment_product_id` 处理规则：

- 如果当前支付通道支持动态价格创建，可以不填 `payment_product_id`。
- 当前 Stripe / PayPal 代码路径支持按服务端 pricing item 动态创建价格。
- 当前 Creem 代码路径要求 `productId`，生产使用 Creem 时必须通过 pricing item、`currencies[]` 或后台 `creem_product_ids` 映射提供真实产品 ID。
- 如果后续其它支付通道依赖固定 Price ID，必须填真实 ID。
- 不要填假的 `payment_product_id`。
- 多币种时，币种级 `currencies[].payment_product_id` 优先于 item 级 `payment_product_id`。

checkout 仍由服务端按 `product_id` 查 pricing item，再取 `amount`、`currency`、`credits`、`valid_days`。不要让前端传金额或积分。

### 4.2 年付发放

第一版年付积分发放口径先统一为：一次性发全年积分，`valid_days = 365`。

选择原因：

- 一次性发全年积分通常只需要改 pricing JSON，更适合第一版只改 en / zh pricing JSON 和必要扣费配置的落地范围。
- 年付按月发放 `1/12` 商业上更稳，但依赖 subscription renewal、周期发放、cron 或计划任务支持，不适合第一版只改 3 个文件。

第一版上线前必须核验：

- 年付 SKU 的 `credits` 是全年总积分。
- 年付 SKU 的 `valid_days` 是 `365`。
- checkout / webhook 会按 pricing item 的 `credits` 和 `valid_days` 一次性发放。
- 不要在第一版只靠 pricing JSON 表达“年付按月发放”；等服务端周期发放能力稳定后，再统一调整为年付按月发放。

### 4.3 前台展示和 Credits 说明

前台只做产品化说明，不暴露内部成本模型。

可以展示：

- 套餐名称、售价、Credits 数量。
- Credits 有效期 / 发放方式。
- 图片和视频共用 Credits。
- 高质量图片和视频会消耗更多 Credits。
- 免费额度只适合 Basic Image 体验。
- 高阶视频 / 自定义视频需要更多 Credits 或联系团队。

必要时只保留少量稳定用量锚点，这些锚点以 `3.本项目定价方案.md` 第 3 节为准。

统一积分套餐的前台表达优先级：

- 套餐卡片主表达：`Credits 数值 + 代表性用量换算`。
- 卡片 feature / tip：`Credits work across image and video generation.`
- FAQ / tooltip：`Higher-quality image and video models use more credits.`

默认推荐英文文案：

- `Good for ~20 Pro images or ~6 Fast 5s videos`
- `≈ 20 Pro images or ~6 Fast 5s videos`
- `Equivalent to ~20 Pro images or ~6 Fast 5s videos`
- `Generates up to ~20 Pro images or ~6 Fast 5s videos`

默认推荐通用说明：

- `Credits are shared across all models. Higher-quality generations consume more credits.`
- `1 credit does not equal 1 generation. Advanced models and higher resolutions require more credits per use.`

执行要求：

- 同一页所有套餐卡片统一一种句式，第一版默认用 `Good for ~...`。
- 用 `Pro images`、`Fast videos` 这类产品化名称，不直接暴露内部模型名、供应商名或 route 名。
- 代表性用量只作为感知锚点，不作为精确承诺；保留 `~`、`≈`、`up to` 这类缓冲符号或措辞。
- 完整扣费差异放在 FAQ / tooltip，不在套餐卡片正文展开完整矩阵。

禁止展示：

- 供应商名称。
- API 成本、供应商报价、成本快照。
- 毛利率、利润、安全线。
- route、fallback、高波动 route。
- 内部积分价值。
- 图片倍数、视频倍数、fallback 倍数。
- 完整模型扣费表或完整能力档位矩阵。

### 4.4 免费额度约束

当前代码默认关闭新用户免费积分：

```text
INITIAL_CREDITS_ENABLED=false
INITIAL_CREDITS_AMOUNT=0
INITIAL_CREDITS_VALID_DAYS=30
INITIAL_CREDITS_DESCRIPTION=initial credits for free trial
```

如产品后续决定开启免费试用，才单独评估是否改为 `5 credits / 7 days`。配置免费积分时必须满足：

- `5 credits` 只覆盖 Basic Image 量级。
- 不要给视频设置低于 `15 credits` 的扣费。
- 不要把 Pro Image、4K Image、Advanced Video 映射到 `5 credits`。
- 不做 `initial_free` ledger。
- 不做 paid credits / free credits 分账。
- 不改 `consumeCredits` 的 FIFO 语义。

## 5. AI 修改步骤

让 AI 改价格和积分时，按这个顺序执行：

1. 读取 `docs/定价/3.本项目定价方案.md` 第 3 节和第 4 节，确认本次要落地的套餐表和模型积分消耗表。
2. 如果是改前台套餐，读取并修改 en / zh pricing JSON，保持非翻译字段完全一致。
3. 如果是图片 / 视频新增模型或调整模型积分，先确认并更新第 3 节「模型积分消耗表」的业务方案，再由 AI 同步修改 `src/config/ai/models.ts`。
4. 不要为图片 / 视频新增模型手工修改生成器 `MODEL_OPTIONS` 或 `src/config/ai/credit-costs.ts`。
5. 只有调整 pricing 模式、扣费查找策略或新增媒体类型等计算规则时，才修改 `credit-costs.ts`。
6. 如涉及前台文案，只调整产品化说明，不新增完整扣费档位表。
7. 扫描确认前端没有传 `costCredits`。
8. 如果改了 TypeScript，运行 `pnpm lint` 和 `npx tsc --noEmit`。

## 6. 验收清单

| 检查项 | 通过标准 |
|---|---|
| 业务来源 | SKU 和新增模型业务定价来自 `docs/定价/3.本项目定价方案.md`；已落地模型注册和扣费执行口径来自 `src/config/ai/models.ts` |
| Pricing 配置源 | 套餐仍以 `pricing.json` 为配置源 |
| en / zh 一致性 | `product_id`、`interval`、`group`、`amount`、`currency`、`credits`、`valid_days` 完全一致 |
| 金额 | `amount` 使用最小货币单位 |
| SKU 展示 | SKU 按 `item.group` 匹配 `groups[].name`，分为 one-time / monthly / yearly 展示 |
| Pricing 布局 | 每个 group 卡片正常展示，组件继续使用静态 `md:grid-cols-*` class |
| 年付 | 第一版一次性发全年积分，`valid_days = 365`，checkout / webhook 按 pricing item 一次性发放；未实现周期发放前不做年付按月发放 |
| Checkout | 服务端仍按 pricing item 取金额和积分 |
| 支付通道 | Stripe / PayPal 动态价格可用；如使用 Creem，已配置真实产品 ID 映射 |
| 扣费配置 | 图片 / 视频扣费必须从 `src/config/ai/models.ts` 的 `pricing` 字段计算；image/video 不允许使用 legacy scene fallback；music 可继续使用 `text-to-music = 10` 的 legacy fallback |
| family key | family key 必须来自 `src/config/ai/models.ts` 的真实 `family` 字符串 |
| 扣费权威 | 前端不传 `costCredits`，后端计算并写入 `ai_task.costCredits` |
| 免费额度 | 当前默认关闭；如后续开启，免费积分只能覆盖 Basic Image 量级 |
| 前台文案 | 不展示供应商、成本、毛利、route、fallback，不维护完整扣费矩阵 |
| 改动范围 | 没有新增 plans、creditPolicy、ledger、cron 等架构改造 |

新增图片 / 视频模型最终还必须逐项确认：

1. `src/config/ai/models.ts` 中对应 `ModelEntry` 已配置 `pricing`。
2. `pricing.mode` 正确：image 使用 `fixed`，video 使用 `perSecond`。
3. image / video 不依赖 legacy scene fallback；未命中明确 `pricing` 时应报错。
4. `family` 没有拼接 resolution、duration、inputBilling 等规格字段。
5. 前端展示积分与后端实际扣费来自同一套 `calculateModelCredits()` / `models.ts.pricing`。
6. 未修改 `pricing.json`、套餐价格、支付 product id、checkout 或 webhook，除非本次任务明确要求调整 SKU。
