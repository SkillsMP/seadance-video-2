# 项目中 AI 图片生成相关的配置

## 写在前面

当前图片生成器已经按 `docs/修改image生成器.md` 完成一轮关键改造。

最重要的变化是：

- 用户在图片生成器里**只选择模型家族**，不再选择 provider
- provider 只作为系统内部执行链路和 fallback 候选存在
- 前端提交的是 `family + candidates`
- 后端在 `/api/ai/generate` 中按顺序尝试 `candidates`
- 成功后按**实际命中的 `provider + model`** 落库

这份文档只描述**当前代码真实行为**，不再保留旧方案说明。

另外要特别区分：

- `image.tsx` 已切到“模型家族 + 自动兜底”
- `video.tsx` / `music.tsx` 目前仍然保留旧的 `provider + model` 选择方式

### 1.3 fallback 优先级怎么表达

当前没有单独的 `priority` 字段。

**同一 `family` 下在 `MODEL_OPTIONS` 里的顺序，就是 fallback 顺序。**

例如 `Nano Banana Pro` 在当前实现里代表：

- 文生图：`kie -> replicate -> fal`
- 图生图：`kie -> replicate -> fal(edit)`

## 3. 配置方式

### 3.1 环境变量

可在 `.env.development` 或 `.env.example` 中配置：

```env
# Kie
KIE_API_KEY=your_kie_api_key
KIE_CUSTOM_STORAGE=true

# Replicate
REPLICATE_API_TOKEN=r8_xxx
REPLICATE_CUSTOM_STORAGE=true

# Fal
FAL_API_KEY=fal_xxx
FAL_CUSTOM_STORAGE=true

# Gemini
GEMINI_API_KEY=AIza...

# R2
R2_UPLOAD_PATH=bananapro-org
R2_ACCESS_KEY=xxx
R2_SECRET_KEY=xxx
R2_BUCKET_NAME=xxx
R2_ENDPOINT=https://xxx.r2.cloudflarestorage.com
R2_DOMAIN=https://your-cdn-domain
```

### 3.2 数据库配置

项目也支持把这些值存到 `config` 表中，由后台管理界面维护。

图片相关常见键：

```ts
{
  kie_api_key: string
  kie_custom_storage: 'true' | 'false'

  replicate_api_token: string
  replicate_custom_storage: 'true' | 'false'

  fal_api_key: string
  fal_custom_storage: 'true' | 'false'

  gemini_api_key: string

  r2_access_key: string
  r2_secret_key: string
  r2_bucket_name: string
  r2_endpoint: string
  r2_domain: string
  r2_upload_path: string
}
```

配置定义位置：

- `src/shared/services/settings.ts`

### 3.3 配置优先级

当前真实逻辑是：

**环境变量优先于数据库配置。**

配置读取逻辑在：

- `src/shared/models/config.ts`

即：

1. 服务端先尝试读数据库配置
2. 再检查 `process.env`
3. 如果环境变量存在，则覆盖同名数据库值

不要再按旧文档理解成“数据库优先”。

## 5. 图片生成器前台生效机制

### 5.1 初始化流程

1. 用户打开图片生成器页面
2. 前端请求 `GET /api/ai/providers`
3. 后端调用 `getAllConfigs()`
4. 根据 API Key 是否存在，返回当前可用 provider 列表
5. 前端根据 `scene + availableProviders` 过滤内部候选项
6. 再按 `family` 去重，得到真正展示给用户的模型列表

### 5.2 `/api/ai/providers` 的判断标准

路由：

- `src/app/api/ai/providers/route.ts`

当前判断逻辑非常直接：

- 有 `kie_api_key` 就返回 `kie`
- 有 `replicate_api_token` 就返回 `replicate`
- 有 `fal_api_key` 就返回 `fal`
- 有 `gemini_api_key` 就返回 `gemini`

注意：

- 这里只检查“是否配置了 key”
- **不验证 key 是否可用**
- 真正调用失败，只会在生成或查询时暴露出来

### 5.3 图片前端状态不再维护 provider

当前 `image.tsx` 的核心状态已经收口为：

```ts
const [selectedFamily, setSelectedFamily] = useState('');
```

然后派生出：

```ts
const availableModelOptions = MODEL_OPTIONS.filter(
  (option) =>
    option.scenes.includes(activeTab) &&
    availableProviders.includes(option.provider)
);

const availableFamilyOptions = dedupeModelFamilies(availableModelOptions);

const selectedCandidates = availableModelOptions.filter(
  (option) => option.family === selectedFamily
);
```

也就是说：

- UI 不再维护 `provider + model` 双状态
- 图片生成器中也不再展示 provider 下拉
- 用户看到的永远是**去重后的 family 列表**

### 5.4 family 自动回退

如果当前 `selectedFamily` 在新场景下不可用：

- 前端会自动回退到第一个合法 family
- 不需要手动同步 provider

这是当前实现中避免“切 tab 后模型失效卡死”的关键保护逻辑。

### 5.5 无可用模型时的表现

如果当前场景下没有可用 family：

- Model `<Select>` 会 disabled
- 生成按钮会 disabled
- 页面会显示提示：
  - `Please contact the administrator to configure AI models.`
  - 或 `No models are available for the current generation mode.`

## 6. 图片生成请求机制

### 6.1 前端提交格式

图片生成器现在提交的不是单个 `provider + model`，而是：

```ts
{
  mediaType: 'image',
  scene: 'text-to-image' | 'image-to-image',
  family: 'nano-banana-pro',
  candidates: [
    { provider: 'kie', model: 'nano-banana-pro' },
    { provider: 'replicate', model: 'google/nano-banana-pro' },
    { provider: 'fal', model: 'fal-ai/nano-banana-pro' },
  ],
  prompt,
  options,
}
```

其中：

- `family` 是用户选择的模型家族
- `candidates` 是前端按当前场景和可用 provider 计算出的有序候选链路

### 6.2 `selectedCandidates` 的约束

`selectedCandidates` 必须同时满足：

- family 匹配
- scene 匹配
- provider 当前可用

这点很重要，因为像 `fal` 的 `Nano Banana Pro`：

- 文生图是 `fal-ai/nano-banana-pro`
- 图生图是 `fal-ai/nano-banana-pro/edit`

如果只按 family 过滤，不按 scene 过滤，会把错误模型混进候选链路。

## 7. 后端生成机制

路由：

- `src/app/api/ai/generate/route.ts`

### 7.1 新旧两条路径并存

当前 `generate` 接口是渐进兼容的：

#### 新路径：图片生成器

当 `mediaType === image` 且 `candidates?.length > 0` 时：

- 后端按顺序尝试 `candidates`
- 哪个 candidate 先成功，就用哪个
- 成功后把实际命中的 `provider + model` 写入 `ai_task`

#### 旧路径：视频 / 音乐

如果请求里直接传了：

```ts
{ provider, model }
```

则仍然走旧逻辑。

这也是为什么：

- 图片生成器已经是 family 模式
- 视频生成器目前还是 provider 下拉模式

### 7.2 fallback 发生在哪个阶段

当前 fallback **只发生在“创建任务阶段”**。

也就是：

- 第一个 provider 创建任务失败，才切下一个 provider
- 一旦远端任务已经成功创建，后续轮询失败不会自动重新换 provider 重建任务

这是有意控制复杂度的结果。

### 7.3 失败日志

如果多个 candidate 都失败：

- 后端会收集 `candidateErrors`
- 服务端日志会记录每个候选项失败原因
- 返回给前端的是统一错误

## 8. 查询、结果回存与 Showcase

### 8.1 轮询查询

路由：

- `src/app/api/ai/query/route.ts`

流程：

1. 前端轮询 `POST /api/ai/query`
2. 后端根据 `task.provider` 找到真实 provider
3. 调用对应 provider 的 `query()` 方法
4. 更新 `ai_task.taskInfo / taskResult / status`
5. 返回任务结果给前端

### 8.2 Custom Storage

如果 provider 开启了 `custom_storage`：

- Kie / Replicate / Fal 在 `query()` 成功时
- 会把 provider 返回的远端图片 URL 下载下来
- 再通过 `saveFiles()` 上传到自己的 R2 / S3
- 最后把结果 URL 替换成自有存储 URL

这意味着：

- `/api/ai/query` 不只是“查状态”
- 它还可能顺手执行“下载远端文件 + 上传自有存储”
- 所以在成功轮询阶段，`query` 可能明显变慢

### 8.3 Showcase 保存链路

图片展示成功后，前端还会额外尝试保存 showcase：

1. `image.tsx` 调用 `saveShowcase`
2. 通过 `/api/proxy/file` 重新下载图片
3. 调用共享压缩函数 `compressImage`
4. 再走 `/api/upload`
5. 最后调用 `/api/showcases/add`

当前共享压缩函数的行为是：

- 输出格式：`webp`
- 质量：`0.7`
- **当前没有额外做尺寸缩放**

对应实现位置：

- `src/shared/blocks/common/image-uploader.tsx`

注意：

- 图片主流程成功，不代表 showcase 一定成功
- showcase 保存失败，不会影响用户已经看到的生成结果

## 10. 配置示例

### 场景 1：只配置 Kie

```ts
kie_api_key = "your_kie_key"
kie_custom_storage = "true"
```

前端效果：

- 图片生成器模型下拉只会出现 Kie 可支持的 family
- `Nano Banana Pro` 可以用于文生图 / 图生图
- 不会显示 provider 下拉
- 实际 candidates 通常只有一个：`kie`

### 场景 2：配置 Kie + Replicate + Fal

```ts
kie_api_key = "your_kie_key"
kie_custom_storage = "true"
replicate_api_token = "your_replicate_token"
replicate_custom_storage = "true"
fal_api_key = "your_fal_key"
fal_custom_storage = "false"
```

前端效果：

- 模型下拉显示的是 family，不是 provider
- 用户会看到：
  - `Nano Banana Pro`
  - `Seedream 4`
  - `Z-Image Turbo`
  - `Flux 2 Flex`
- 例如 `Nano Banana Pro` 的内部候选链路可能是：
  - 文生图：`kie -> replicate -> fal`
  - 图生图：`kie -> replicate -> fal(edit)`

### 场景 3：配置所有图片 Provider

```ts
kie_api_key = "your_kie_key"
kie_custom_storage = "true"
replicate_api_token = "your_replicate_token"
replicate_custom_storage = "true"
fal_api_key = "your_fal_key"
fal_custom_storage = "true"
gemini_api_key = "your_gemini_key"
```

前端效果：

- 用户依然只看到模型家族
- 不会看到 `Kie / Replicate / Fal / Gemini` 作为图片 provider 选择器
- 实际命中的 provider 由后端根据 `candidates` 顺序决定

### 场景 4：未配置任何图片 Provider

```ts
// 所有图片相关 API Key 都为空
```

前端效果：

- `/api/ai/providers` 返回空数组
- `availableFamilyOptions` 为空
- 模型下拉禁用
- 生成按钮禁用
- 页面提示联系管理员配置 AI models

## 12. 总结

当前图片生成器的核心机制可以概括为：

### 配置层

- 是否可用由 provider 的 API Key 决定
- 环境变量优先于数据库配置

### 前端层

- 用户只选模型家族
- 前端根据 `scene + availableProviders` 计算 `candidates`
- family 无效时自动回退

### 后端层

- 图片生成优先走 `candidates` fallback
- 视频 / 音乐暂时继续走旧路径
- 任务记录按实际命中的 `provider + model` 落库

### 存储层

- 若启用 `custom_storage`，查询成功时会把远端文件回存到自有存储
- 图片结果展示后还会额外尝试保存到 showcase

一句话总结：

**现在的图片生成器已经不是“用户选择 provider 上的模型”，而是“用户选择模型家族，系统自动决定用哪个 provider 执行”。**
