# Reference-to-Video MVP 方案

> 文档状态：待实施，仅作为开发方案，不代表功能已经上线  
> 项目：`bananapro-org`  
> 上游服务商：Kie.ai  
> 首个模型：MiniMax H3（Hailuo 03）  
> 适用范围：Phase 3 / Phase 4  
> 文档日期：2026-08-03

本文件承接 [MiniMax H3 基础接入方案](<8.3_MiniMax H3 基础接入方案.md>) 中延后的 Reference-to-Video 能力。它是独立的多模态 Workflow，不是 H3 Text-to-Video / Image-to-Video 的前置依赖。

## 1. 结论与范围

Reference-to-Video 使用独立 scene：

```text
scene: reference-to-video
model: minimax-h3/reference-to-video
```

它不能伪装成现有 `video-to-video` 或 Image-to-Video `reference_images` 模式，因为输入结构、媒体可信度、服务端校验和计费口径都不同。

本 MVP 只实现：

- 生成页内的图片、视频和音频参考输入。
- 项目上传产生的短期 receipt。
- 服务端 canonical metadata 和可信时长/大小/MIME。
- Reference 媒体数量、格式、大小、时长和组合校验。
- 固定或按业务明确启用的动态网站计费。
- H3 的独立 Provider payload builder。
- 独立启用、独立 smoke test 和独立回滚。

本 MVP 不建设：

```text
素材库、历史素材复用、后台媒体管理
异步转码、媒体分析平台、媒体元数据数据库
按模型动态 upload policy 服务
Provider 成本平台和成本告警
跨 Provider payload DSL
Webhook 强依赖链路
现有 Seedance workflow 迁移
```

Seedance 或其他视频模型未来支持 Reference-to-Video 时，可以复用本文件定义的 scene、上传 receipt、可信元数据和 UI；必须使用自己的 `referenceInputs` 约束和 Provider builder，不迁移现有 Seedance 逻辑。

## 3. 模型级 Reference 约束

Reference 类型只在进入本阶段时加入基础 `ModelInputConstraints`：

```ts
interface ReferenceMediaConstraints {
  maxCount: number;
  maxSizeMB: number;
  allowedMimeTypes: readonly string[];
  minDurationSeconds?: number;
  maxDurationSeconds?: number;
  maxTotalDurationSeconds?: number;
}

interface ReferenceInputConstraints {
  images?: ReferenceMediaConstraints;
  videos?: ReferenceMediaConstraints;
  audios?: ReferenceMediaConstraints;
  requireVisualInput?: boolean;
}

interface ModelInputConstraints {
  // 基础 H3 方案已有字段
  imageModes?: readonly VideoImageMode[];
  promptRequired?: boolean;
  uploadMaxSizeMB?: number;

  // Phase 3 才增加
  referenceInputs?: ReferenceInputConstraints;
}
```

H3 Reference 约束：

```ts
inputConstraints: {
  'reference-to-video': {
    promptRequired: true,
    referenceInputs: {
      images: {
        maxCount: 9,
        maxSizeMB: 30,
        allowedMimeTypes: ['image/jpeg', 'image/png', 'image/webp'],
      },
      videos: {
        maxCount: 3,
        maxSizeMB: 50,
        allowedMimeTypes: ['video/mp4', 'video/quicktime'],
        minDurationSeconds: 2,
        maxDurationSeconds: 15,
        maxTotalDurationSeconds: 15,
      },
      audios: {
        maxCount: 3,
        maxSizeMB: 15,
        allowedMimeTypes: ['audio/wav', 'audio/x-wav', 'audio/mpeg'],
        minDurationSeconds: 2,
        maxDurationSeconds: 15,
        maxTotalDurationSeconds: 15,
      },
      requireVisualInput: true,
    },
  },
}
```

Reference 图片 MVP 只开放 JPEG、PNG 和 WebP。HEIC / HEIF 等格式等上传、浏览器预览、元数据识别、对象存储和目标运行时全部验证通过后再加入。

媒体组合规则：

- 图片数量 `0–9`。
- 视频数量 `0–3`。
- 音频数量 `0–3`。
- 图片和视频至少存在一种。
- 音频不能单独存在。
- 每个媒体满足当前模型的 MIME、大小和单文件时长限制。
- 参考视频总时长不超过 15 秒。
- 参考音频总时长不超过 15 秒。
- 生成时长使用模型声明的 4–15 秒整数选项。

不要把上述数字写死在通用组件或通用校验函数中，统一从所选 `ModelEntry` 的 `referenceInputs` 读取。

## 4. 生成页 Workflow

新增独立 `reference-to-video` tab 和模型无关组件：

```text
src/shared/blocks/generator/video-reference-inputs.tsx
```

组件只根据当前模型约束展示：

- 图片、视频和音频输入区。
- 每种媒体的数量和大小限制。
- 视频、音频单个时长与总时长限制。
- 必须存在视觉输入等组合规则。
- 当前网站积分预估。

客户端只提交凭证和普通控件：

```ts
{
  reference_media_receipts: string[];
  duration: number;
  aspect_ratio?: string;
}
```

`src/config/ai/options.ts` 必须为新 scene 登记唯一的媒体输入字段：

```ts
const SCENE_INPUT_OPTIONS: Record<string, Set<string>> = {
  // 现有配置……
  'reference-to-video': new Set(['reference_media_receipts']),
};
```

options 层只做基础形状校验：`reference_media_receipts` 必须是非空、去除首尾空白后仍非空的字符串数组。它不解析签名，也不相信 receipt 内的媒体事实；签名、归属、有效期和 canonical metadata 由 `reference-media.ts` 验证。直接 URL、媒体大小、MIME、时长等替代字段不加入 scene 白名单；如果 URL 被伪装成 receipt 字符串，receipt 服务必须拒绝。

客户端不能提交：

```text
image_input
video_input
audio_input
reference_image_urls
reference_video_urls
reference_audio_urls
input_video_duration
size / mime / mediaType
```

模型切换只更新当前约束，不自动删除素材：

- 新模型不支持当前媒体类型时，切换到可用的默认输入视图。
- 原模式素材保留为草稿，不再合法的素材显示错误。
- 超过数量、大小或时长限制时禁用 Generate。
- 用户可以移除素材或切回原模型。

这样能保留用户输入，又不会引入素材库或跨模型资产管理。

## 5. 上传、receipt 与可信元数据

Reference MVP 新增一个共用媒体上传入口，不为 H3 分别建立图片、视频、音频接口：

```text
src/app/api/storage/upload-media/route.ts
```

上传流程：

1. 要求用户已登录，并使用现有架构可实现的上传频率和文件数量限制。
2. 服务端按明确 allowlist 校验 MIME、扩展名和平台硬上限。
3. 使用与目标部署运行时兼容的成熟媒体解析器读取必需的 duration、容器和 MIME；不手写媒体格式解析器。
4. 上传到项目对象存储并生成 HTTPS URL。
5. 返回前端预览所需元数据，并签发短期防篡改 receipt。
6. `/api/ai/generate` 验证 receipt，重新构造 canonical metadata，再执行约束和计费。

receipt 至少签名：

```text
version + ownerId + storageKey + mediaType + duration + size + mime + expiresAt
```

验证时必须：

- 检查当前用户与 `ownerId` 一致。
- 从 `storageKey` 恢复项目对象存储 URL，不信任客户端回传 URL。
- 检查 HTTPS、存储域名、媒体命名空间和 receipt 有效期。
- 拒绝 localhost、私有 IP、保留 IP、link-local 地址和带认证信息的 URL。
- 使用独立服务端签名密钥，不使用 Kie API Key、Webhook Key 或用户可见配置。

服务端验证后得到内部 canonical metadata：

```ts
interface VerifiedReferenceMedia {
  url: string;
  storageKey: string;
  mediaType: 'image' | 'video' | 'audio';
  mime: string;
  size: number;
  duration?: number;
}
```

该类型只属于服务端媒体服务，用于计费和 Reference 约束校验。`reference-media.ts` 应使用：

```ts
import 'server-only';
```

它不被客户端引用，也不向通用 Provider 类型反向导入服务实现。目标运行时必须先完成 MP4、MOV、WAV、MP3 元数据解析和大文件内存占用 spike；无法可靠获得可信时长时，Reference entry 保持 `enabled: false`。

## 6. 校验函数与 Provider 内部上下文

基础 H3 的 `assertModelInputConstraints()` 不接收 Reference 媒体。Reference receipt 验证成功后单独执行：

```ts
assertReferenceMediaConstraints({
  entry,
  scene,
  media: verifiedReferenceMedia,
});
```

该函数只在 `reference-to-video` scene 调用，负责媒体类型、数量、MIME、大小、单文件时长、总时长和组合规则。它可以与 receipt 验证共同放在 `src/shared/services/reference-media.ts`，但不建设通用能力矩阵或校验框架。

### 6.1 纯类型与最小 Provider DTO

通用 `src/extensions/ai/types.ts` 被客户端组件和多个 Provider 使用，因此只能放纯类型，不能导入 `reference-media.ts`，也不能加入 `server-only`：

```ts
export interface AIVerifiedReferenceMedia {
  mediaType: 'image' | 'video' | 'audio';
  url: string;
}

export interface AIProviderContext {
  verifiedReferenceMedia?: readonly AIVerifiedReferenceMedia[];
}

export interface AIGenerateParams {
  // 现有字段保持不变……
  providerContext?: AIProviderContext;
}
```

服务端从完整 canonical metadata 映射出 Provider DTO：

```ts
const providerContext: AIProviderContext = {
  verifiedReferenceMedia: verifiedReferenceMedia.map(({ mediaType, url }) => ({
    mediaType,
    url,
  })),
};
```

`providerContext` 必须满足：

- 不从请求 JSON 读取。
- 不进入 options 白名单。
- 在 receipt 验证成功后由服务端构造。
- fallback candidates 复用同一份已验证 Provider DTO。
- 不序列化进 `ai_task.options`。
- 不自动透传给上游。
- `storageKey`、大小、MIME、时长和完整 receipt 不进入 Provider DTO。

### 6.2 receipt 剥离与任务落库

`reference_media_receipts` 只允许在请求解析和 receipt 验证阶段短暂存在。验证前后必须显式拆分请求输入、Provider options 和任务落库 options，不能继续复用同一个 options 对象：

```ts
const { reference_media_receipts: receipts, ...businessOptions } =
  resolvedOptions;

const verifiedReferenceMedia = await verifyReferenceMediaReceipts(receipts);

const referenceMediaSummary = {
  imageCount,
  videoCount,
  audioCount,
  inputVideoDuration,
};

const providerOptions = businessOptions;
const taskOptions = {
  ...businessOptions,
  reference_media_summary: referenceMediaSummary,
};
```

三类对象的边界必须固定：

```text
resolvedOptions
→ 可以短暂包含 receipt，仅用于服务端验证

providerOptions
→ 不包含 receipt、URL 数组或可信媒体元数据

taskOptions / ai_task.options
→ 不包含 receipt、URL、storageKey 或签名材料
→ 只允许保存生成参数和非敏感统计摘要

providerContext
→ 只包含服务端生成的 mediaType + URL
```

`reference_media_summary` 是服务端派生的审计/展示摘要，不接受客户端同名字段，也不发送给 Provider。若当前产品没有读取摘要的实际需求，可以不落该字段；但 receipt 仍必须从 `ai_task.options` 中剥离。

生成入口顺序：

```text
findModel / 校验 candidates
→ sanitize / resolve controls
→ 从 resolvedOptions 剥离 reference receipts
→ 验证 receipts，得到 VerifiedReferenceMedia
→ assertModelInputConstraints
→ assertReferenceMediaConstraints
→ 计算服务端网站积分
→ 检查余额
→ 映射最小 providerContext
→ Provider builder
→ 使用不含 receipt 的 taskOptions 创建任务、落库并扣积分
```

Provider 创建失败沿用现有行为：不创建业务任务、不扣积分；异步失败复用现有幂等退款逻辑。

## 7. H3 Reference Provider Builder

`KieProvider.generateVideo()` 只从内部上下文取出 `AIVerifiedReferenceMedia[]`，不解析 receipt、不访问 storage key：

```ts
const referenceMedia = params.providerContext?.verifiedReferenceMedia;
```

H3 Reference builder 只允许：

```text
model
input.prompt
input.reference_image_urls（非空时）
input.reference_video_urls（非空时）
input.reference_audio_urls（非空时）
input.aspect_ratio（配置或默认值存在时）
input.duration
```

映射：

```text
mediaType=image -> reference_image_urls
mediaType=video -> reference_video_urls
mediaType=audio -> reference_audio_urls
```

Builder 不接收客户端 receipt、任意 URL、网站积分、Provider 成本或内部媒体元数据。未来 Seedance 等模型新增 Reference scene 时，使用自己的 builder，不把 H3 字段加入通用 Kie Set。

## 8. 网站计费

先由业务确定固定或动态网站积分，不直接等同 Kie 成本。

无论选择固定还是动态计费，`src/config/ai/credit-costs.ts` 都必须先登记新 scene，保证 `GenerationScene` 类型完整：

```ts
export type GenerationScene =
  | 'text-to-image'
  | 'image-to-image'
  | 'text-to-video'
  | 'image-to-video'
  | 'video-to-video'
  | 'reference-to-video';
// 现有其他 scene……
```

这是新增 Workflow 的基础类型改动，不以动态计费为条件。只有输入视频时长和额外图片的计算字段、公式才是动态计费的条件改动。

### 8.1 固定计费

如果业务选择保守的固定 `creditsPerSecond` 覆盖最坏输入成本，优先不增加动态计费字段，只使用可信 metadata 做约束和风控。

### 8.2 动态计费

只有业务明确按输入视频时长或第 6 张起的参考图片向用户收费时，才在现有计费层做最小扩展：

```ts
interface ScenePricing {
  // 现有字段……
  creditsPerInputVideoSecond?: number;
  includedReferenceImages?: number;
  creditsPerExtraReferenceImage?: number;
}
```

公式由业务价格决定：

```text
siteCredits =
  generatedDuration × creditsPerSecond
  + trustedInputVideoDuration × creditsPerInputVideoSecond
  + max(0, trustedImageCount - includedReferenceImages)
    × creditsPerExtraReferenceImage
```

前端预估可以使用上传响应元数据；服务端扣费必须使用 receipt 验证后的 canonical metadata。两者调用同一计费规则并增加一致性测试。

## 10. 分阶段实施

### Phase 3：通用 Reference Workflow

1. 在目标运行时验证 MP4、MOV、WAV、MP3 元数据解析、内存占用和超时。
2. 确认 receipt 签名密钥来源、有效期和对象存储来源限制。
3. 增加 `reference-to-video` scene、tab 和通用多媒体输入组件。
4. 在 `options.ts` 登记 receipt 输入并完成基础形状校验，在 `credit-costs.ts` 登记新 Scene 类型。
5. 增加媒体上传、canonical metadata、receipt 签发和验证。
6. 增加 `referenceInputs` 和 `assertReferenceMediaConstraints()`。
7. 显式剥离 receipt，分别构造 Provider options、task options 和最小 `providerContext`。
8. 完成 URL 安全、服务端组合规则和动态/固定计费选择。
9. 完成 Reference 聚合 contract test。

如果目标运行时无法可靠获得可信 duration，Reference entry 必须保持 `enabled: false`。

### Phase 4：H3 Reference Adapter

1. 注册 `minimax-h3/reference-to-video`，保持 `enabled: false`。
2. 完成 H3 Reference payload 分支和字段白名单。
3. 完成图片、视频、视频 + 音频等真实请求测试。
4. 验证任务创建、轮询、结果转存、积分扣除和失败退款。
5. 通过独立门槛后再启用 H3 Reference，不影响已上线的 H3 Text/Image。

## 11. 测试与上线门槛

静态和单元测试必须覆盖：

- receipt 过期、签名错误、字段篡改、用户归属错误和非项目 URL 被拒绝。
- `reference_media_receipts` 不是非空字符串数组时由 options 层拒绝，直接 URL 或媒体元数据替代字段不被放行。
- JPEG、PNG、WebP 允许；HEIC / HEIF 在 MVP 被拒绝。
- 图片、视频、音频数量和视觉输入组合规则。
- 单文件大小、单文件时长和总时长限制。
- 客户端伪造 duration、size、mime、mediaType 不影响服务端校验和扣费。
- `assertReferenceMediaConstraints()` 与 `assertModelInputConstraints()` 各自只校验自己的边界。
- receipt 从 Provider options 和 `ai_task.options` 中剥离；任务摘要不包含 URL、storage key 或签名材料。
- `providerContext` 不进入 `ai_task.options`，也不发送 receipt、storage key 或内部计费字段。
- H3 payload 不含 callback、resolution、generate_audio、n_frames 等未声明字段。

真实 smoke 至少覆盖：

```text
4 秒图片 Reference-to-Video
4 秒视频 Reference-to-Video
4 秒视频 + 音频 Reference-to-Video
超过 5 张图片的计费/成本对账场景
```

Reference entry 只有同时满足以下条件后才设为 `enabled: true`：

- 目标运行时媒体解析和大文件上传已验证。
- receipt、URL 来源和媒体归属验证通过。
- 网站固定或动态计费已确定，前后端扣费一致。
- H3 Reference payload contract test 和真实 smoke 通过。
- 任务轮询、结果转存、失败退款和幂等行为通过。
- H3 Text/Image 已有功能不受影响。

## 12. 回滚与复用

Reference 发生问题时只关闭 `reference-to-video` scene 或 H3 Reference entry：

1. 设置 `minimax-h3/reference-to-video` 为 `enabled: false`。
2. 从 Reference tab 和服务端可用模型中移除该 entry。
3. 保留已创建任务的查询、结果处理和历史落库。
4. 不关闭 H3 Text-to-Video / Image-to-Video，也不回滚 Seedance。

以后其他视频模型复用 Reference Workflow 时，只新增对应 scene entry、真实 `referenceInputs`、网站定价、Provider builder、contract test 和 smoke test。通用上传、receipt 和 UI 可以复用，但不同模型的字段、媒体组合和计费规则必须保持独立。
