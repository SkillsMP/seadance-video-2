# 图片生成成功但出现错误弹窗：保守修复方案

## 背景

当前图片可以正常生成，并且能在页面上显示，但开发环境控制台和页面提示里仍可能出现错误。

从现有代码和日志看，主要来自两个后置流程：

1. `/api/ai/query` 轮询任务状态时，偶发网络超时。
2. `saveShowcase` 自动保存展示图时，上传接口偶发失败。

这两个问题不等同于图片生成主流程失败，不应该直接让用户看到“生成失败”级别的错误。

---

## 目标

本次修改只解决当前误报问题，原则是：

- 最小入侵。
- 不重构主流程。
- 不修改后端接口协议。
- 不新增全局工具函数。
- 不封装复杂 retry 体系。
- 不把后置失败误判为生成失败。
- 保留必要日志，便于排查。

---

## 不做的事

暂时不做以下改动：

1. 不修改 `/api/ai/query` 的 HTTP 状态码返回逻辑。
2. 不改 `respErr()` 的统一响应结构。
3. 不封装全局 `fetchWithRetry`。
4. 不重构 `saveShowcase`。
5. 不调整 Kie Provider 主逻辑。
6. 不新增一套错误分类系统。
7. 不检查 `/api/showcases/add` 的响应结果。

原因：这些改动影响面更大，或者不属于当前体验问题的核心。当前问题可以通过前端轻量容错和日志降级解决。

---

## 最终改动范围

只改一个文件：

```txt
src/shared/blocks/generator/image.tsx
```

只做 3 个极小改动：

1. `pollTaskStatus` 增加连续失败计数。
2. 任务重置时清零轮询失败计数。
3. `saveShowcase` 失败日志从 `console.error` 降级为 `console.warn`。

---

## 改动 1：轮询增加连续失败容忍

### 当前问题

当前 `pollTaskStatus` 在任何一次查询失败后，会立即：

- `toast.error(...)`
- `resetTaskState()`
- 停止轮询
- 刷新积分

这会把一次偶发网络错误升级成用户可见失败。

### 修改方案

在已有 ref 附近增加一个连续失败计数器：

```ts
const savedTaskIdsRef = useRef<Set<string>>(new Set());
const queryFailCountRef = useRef(0);
```

在 `/api/ai/query` 返回正常，并且 `code === 0` 后重置计数：

```ts
const { code, message, data } = await resp.json();

if (code !== 0) {
  throw new Error(message || 'Query task failed');
}

queryFailCountRef.current = 0;
```

将 `pollTaskStatus` 的 catch 从“失败一次就结束”改为“连续失败 3 次才结束”：

```ts
} catch (error: any) {
  queryFailCountRef.current += 1;

  console.warn(
    `Polling image task failed (${queryFailCountRef.current}/3), will retry:`,
    error
  );

  if (queryFailCountRef.current < 3) {
    return false;
  }

  console.error('Error polling image task:', error);
  toast.error(`Query task failed: ${error.message}`);
  resetTaskState();

  fetchUserCredits();

  return true;
}
```

### 预期收益

- 偶发网络抖动不会立刻打断生成流程。
- 已生成图片不会因为一次查询失败而被误判为失败。
- 连续失败后仍然保留真实错误提示。
- 不改变现有轮询结构。

---

## 改动 2：任务重置时清零失败计数

### 当前问题

`queryFailCountRef` 是跨 render 保存的状态。如果不主动清零，可能把上一次任务的失败次数带到下一次任务。

保守代码应该保证：

```txt
任务结束或重置时，轮询失败计数归零，避免污染下一次生成
```

### 修改方案

把清零逻辑放进 `resetTaskState()`，集中、简单，不增加额外状态：

```ts
const resetTaskState = useCallback(() => {
  setIsGenerating(false);
  setProgress(0);
  setTaskId(null);
  setGenerationStartTime(null);
  setTaskStatus(null);
  queryFailCountRef.current = 0;
}, []);
```

这样成功、失败、超时、连续查询失败等终态都会统一清理失败计数。

---

## 改动 3：Showcase 保存失败日志降级

### 当前问题

`saveShowcase` 是图片生成后的附加流程。它失败时，不应该影响图片生成成功状态。

当前函数内部已经捕获异常，不会继续向外抛出，但使用了 `console.error`。在 Next.js dev 环境中，这类错误可能会被展示成醒目的 Console Error。

### 修改方案

将 `saveShowcase` 的失败日志从 `console.error` 降级为 `console.warn`。

原代码：

```ts
} catch (error) {
  console.error('Failed to save showcase:', error);
  savedTaskIdsRef.current.delete(taskIdForTracking);
}
```

改为：

```ts
} catch (error) {
  console.warn('Failed to save showcase, ignored:', error);
  savedTaskIdsRef.current.delete(taskIdForTracking);
}
```

### 预期收益

- 图片生成成功时，不再因为展示图保存失败出现红色错误。
- 自动保存失败仍有日志可查。
- 不影响后续同一任务再次尝试保存，因为失败后仍会从 `savedTaskIdsRef` 删除。

---

## 验收标准

### 场景 1：图片生成成功，某一次轮询超时

预期结果：

- 页面继续轮询。
- 不立刻弹出错误 toast。
- 后续轮询成功后正常展示图片。

### 场景 2：连续 3 次轮询失败

预期结果：

- 停止生成状态。
- 显示 `Query task failed` 错误。
- 刷新用户积分。
- 失败计数被清零。

### 场景 3：图片已生成，但 showcase 上传失败

预期结果：

- 图片仍然正常展示。
- 不影响生成成功提示。
- 控制台仅输出 warning。

### 场景 4：连续失败后重新发起新任务

预期结果：

- 新任务从 0 次查询失败开始计数。
- 不会继承上一次任务的失败次数。

---

## 总结

本方案不追求一次性解决所有潜在网络问题，只针对当前最明显的误报做保守修复。

核心思路是：

- 主流程失败才提示用户失败。
- 后置流程失败只记录 warning。
- 偶发网络错误先继续轮询，不立即中断。
- 任务结束时清理轮询失败计数，避免跨任务污染。

这版改动足够小，不扩散到后端和 Provider，也不会让生成器代码变重。
